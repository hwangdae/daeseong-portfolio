<p>Next.js에서 httpOnly 쿠키로 인증 시스템 만들기 (feat. BFF 패턴)</p><h2>들어가며</h2><p>로그인 기능을 구현할 때 가장 먼저 마주치는 질문은 "토큰을 어디에 저장할 것인가"입니다.</p><p><code>localStorage</code>는 구현이 간단하지만 XSS 공격에 그대로 노출됩니다. 서드파티 스크립트 하나만 뚫려도 토큰이 통째로 유출될 수 있습니다. 반대로 <code>httpOnly</code> 쿠키는 자바스크립트로 접근할 수 없어 안전하지만, SSR 환경인 Next.js에서는 "그럼 서버 컴포넌트는 어떻게 인증 상태를 알지?", "미들웨어에서는 어떻게 검증하지?" 같은 새로운 고민이 생깁니다.</p><p>이 글에서는 운동다짐(gym) 프로젝트에서 <strong>BFF(Backend For Frontend) 패턴</strong>과 <strong>httpOnly 쿠키</strong>를 조합해 이 문제를 해결한 과정을 정리합니다.</p><h2>왜 BFF 패턴인가</h2><p>기존 SPA 방식에서는 브라우저가 백엔드 API를 직접 호출합니다.</p><pre><code class="language-plaintext">Browser ──&gt; Backend API (Authorization: Bearer xxx)</code></pre><p>이 구조의 문제는 명확합니다.</p><ul><li><p>브라우저가 직접 <code>Authorization</code> 헤더를 만들어야 하므로, 토큰을 JS에서 접근 가능한 저장소(<code>localStorage</code> 등)에 둘 수밖에 없습니다.</p></li><li><p>쿠키로 토큰을 주고받으려면 <code>SameSite</code>, <code>Secure</code>, CORS 설정을 프론트와 백엔드 양쪽에서 맞춰야 합니다.</p></li></ul><p>그래서 Next.js를 BFF 레이어로 하나 더 두는 구조를 선택했습니다.</p><pre><code class="language-plaintext">Browser ──(Cookie 자동 전송)──&gt; Next.js (BFF) ──(Authorization Header)──&gt; Backend API</code></pre><p>브라우저는 항상 같은 도메인인 Next.js 서버와만 통신하고, 쿠키는 브라우저가 알아서 실어 보냅니다. Next.js Route Handler가 쿠키에서 토큰을 꺼내 <code>Authorization: Bearer &lt;token&gt;</code> 헤더로 변환해 실제 백엔드에 전달하는 역할을 맡습니다. 이렇게 하면 클라이언트 코드는 토큰의 존재 자체를 몰라도 되고, CORS 이슈도 자연히 줄어듭니다.</p><h2>쿠키 설계: httpOnly + Refresh Token Rotation</h2><p>토큰은 두 종류를 사용합니다.</p><ul><li><p><strong>Access Token</strong>: httpOnly 쿠키에 저장하며, 만료 시간은 15분입니다.</p></li><li><p><strong>Refresh Token</strong>: httpOnly 쿠키에 저장하며, 만료 시간은 7일입니다.</p></li></ul><p>쿠키 옵션은 아래처럼 고정합니다 (<code>src/shared/lib/auth/cookies.ts</code>).</p><pre><code class="language-typescript">const COOKIE_OPTIONS = {
  httpOnly: true, // XSS 방지: JS에서 절대 접근 불가
  secure: process.env.NODE_ENV === "production",
  sameSite: "lax" as const, // CSRF 방지
  path: "/",
};</code></pre><p>Access Token의 수명을 짧게(15분) 잡고 Refresh Token으로 재발급받는 이유는, 탈취되더라도 피해 시간을 최소화하기 위해서입니다. 재발급 시에는 새 Refresh Token도 함께 내려주는 <strong>RTR(Refresh Token Rotation)</strong> 정책을 적용해서, 하나의 Refresh Token이 여러 번 재사용되는 것을 막습니다.</p><h2>처음엔 미들웨어에서 갱신하려고 했습니다 (그리고 실패했습니다)</h2><p>지금 구조에 도달하기 전, 첫 버전은 재발급 로직을 미들웨어 안에 통째로 넣었습니다.</p><pre><code class="language-typescript">// access token 없고 refresh token만 있으면 토큰 재발급 시도
if (!accessToken &amp;&amp; refreshToken) {
  const refreshRes = await fetch(`${process.env.NEXT_PUBLIC_API_URL}/auth/refresh`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ refreshToken }),
  });

  if (!refreshRes.ok) {
    const response = isProtected
      ? NextResponse.redirect(new URL("/login", request.url))
      : NextResponse.next();
    response.cookies.delete("accessToken");
    response.cookies.delete("refreshToken");
    return response;
  }

  const { accessToken: newAccessToken, refreshToken: newRefreshToken } = await refreshRes.json();
  const response = NextResponse.next();
  response.cookies.set("accessToken", newAccessToken, { /* ... */ });
  if (newRefreshToken) response.cookies.set("refreshToken", newRefreshToken, { /* ... */ });
  return response;
}</code></pre><p>의도는 단순했습니다. "미들웨어는 모든 요청의 진입점이니, 여기서 한 번에 갱신을 끝내면 그 뒤 로직은 항상 유효한 토큰만 보게 된다." 그리고 실제로 페이지에 처음 진입할 때는 이 로직이 문제없이 잘 동작하는 것처럼 보였습니다. 진입 시점엔 Access Token이 아직 살아있으니 애초에 갱신 분기를 탈 일이 없었기 때문입니다.</p><p>문제는 그 페이지에 <strong>가만히 머물러 있다가 Access Token 수명(15분)이 지난 뒤</strong>, 다시 뭔가를 시도하는 순간 나타났습니다.</p><p>미들웨어는 시간을 감시하는 데몬이 아닙니다. 브라우저 탭을 띄워둔 채 15분이 지나도 미들웨어는 아무 일도 하지 않습니다. 그 시간 동안 새로운 요청이 하나도 발생하지 않았기 때문입니다. 문제는 그 이후, 페이지에서 찜하기를 누르거나 댓글을 남기는 등 <strong>첫 액션이 fetch를 쏘는 순간</strong> 터집니다.</p><p>이 액션 요청이 미들웨어를 통과하면서 위 코드의 <code>if (!accessToken &amp;&amp; refreshToken)</code> 분기를 처음으로 타고, "Access Token이 없다"는 것을 감지해 갱신을 시도합니다. 여기까지는 의도대로입니다. 문제는 갱신에 성공해도 그 결과가 <strong>정작 이 요청 자체에는 반영되지 않는다</strong>는 점이었습니다.</p><p><code>response.cookies.set(...)</code>으로 저장한 새 토큰은 브라우저로 가는 응답 헤더(<code>Set-Cookie</code>)에만 실립니다. 하지만 <code>NextResponse.next()</code>로 이어지는 다음 단계(실제로 그 액션을 처리하는 Route Handler나 서버 로직)가 <code>next/headers</code>의 <code>cookies()</code>로 읽는 값은 <strong>이번 요청이 들어올 때 이미 확정된 request 쿠키</strong>, 즉 방금 막 만료된 옛 Access Token입니다. 결과적으로 다음과 같은 일이 벌어집니다.</p><ol><li><p>사용자가 페이지에 15분 넘게 머물다 찜하기를 누릅니다.</p></li><li><p>미들웨어가 만료를 감지하고 백그라운드에서 토큰 갱신에 성공합니다. (브라우저 쿠키는 곧 최신 상태로 바뀝니다.)</p></li><li><p>그런데 정작 사용자가 방금 누른 "찜하기" 요청 자체는 여전히 옛 토큰을 들고 백엔드로 가서 401을 받고 실패합니다.</p></li><li><p>사용자 입장에서는 "분명 로그인해놨는데 액션이 실패한다"는 이해할 수 없는 버그로 보입니다. 심지어 새로고침하면(=새 요청 = 이미 갱신된 쿠키 사용) 멀쩡하게 동작하니 재현하기도 까다롭습니다.</p></li></ol><p>즉, 진입 시점엔 갱신 로직이 아예 실행되지 않아서 멀쩡해 보였을 뿐이고, 실제 버그는 "페이지에 머무는 동안 토큰이 만료된 뒤의 첫 요청"에서만 나타나는, 미들웨어의 요청 단위 실행 구조 자체에서 비롯된 문제였습니다. 미들웨어가 쿠키를 갱신해도 그 갱신은 "다음 요청부터" 유효하지, "지금 이 요청"에는 적용되지 않는다는 근본적인 한계입니다.</p><p>그래서 갱신 책임을 미들웨어에서 완전히 걷어내고, 실제로 백엔드를 호출하는 지점(공통 fetcher)으로 옮겼습니다. fetcher는 요청을 보내고 401을 받으면 그 즉시, <strong>같은 흐름 안에서</strong> 토큰을 갱신한 뒤 원래 요청을 재시도합니다. "다음 요청부터 유효"가 아니라 "이 요청부터 유효"하게 만든 것이 핵심 차이입니다. 미들웨어는 다시 "토큰이 아예 있는지 없는지"만 보는 가벼운 역할로 되돌아갔습니다.</p><h2>서버 사이드에서 401을 만나면: 자동 재발급</h2><p>가장 까다로웠던 부분은 "Access Token이 만료된 순간을 사용자가 눈치채지 못하게" 만드는 것이었습니다. 이 문제는 공통 fetcher(<code>src/shared/api/serverFetcher.ts</code>) 레벨에서 해결했습니다.</p><pre><code class="language-typescript">let response = await callBackend(path, options, accessToken);

if (response.status === 401 &amp;&amp; !isPublic) {
  const refreshToken = cookieStore.get("refreshToken")?.value;

  if (refreshToken) {
    const refreshed = await refreshAccessToken(refreshToken);

    if (refreshed) {
      await setAuthCookies(refreshed.accessToken, refreshed.refreshToken ?? null);
      response = await callBackend(path, options, refreshed.accessToken);
    } else {
      await clearAuthCookies();
    }
  }
}</code></pre><p>흐름은 이렇습니다.</p><ol><li><p>요청을 보냈는데 401이 옵니다.</p></li><li><p>쿠키에 있는 Refresh Token으로 <code>/auth/refresh</code>를 호출해 새 토큰 쌍을 받습니다.</p></li><li><p>성공하면 쿠키를 갱신하고, 원래 요청을 새 토큰으로 재시도합니다.</p></li><li><p>Refresh Token까지 만료됐다면 쿠키를 모두 지우고 미인증 상태로 처리합니다.</p></li></ol><p>호출하는 쪽(서버 컴포넌트, Route Handler)은 이 로직을 전혀 신경 쓸 필요가 없습니다. <code>serverFetcher.get("/users/me")</code> 한 줄이면 토큰 만료 여부와 무관하게 항상 최신 상태로 응답이 옵니다.</p><h2>미들웨어로 라우트 보호하기</h2><p>인증 여부에 따른 페이지 접근 제어는 <code>middleware.ts</code>에서 처리합니다.</p><pre><code class="language-typescript">const PROTECTED_ROUTES = ["/mypage", "/admin"]; // 로그인 필요
const AUTH_ROUTES = ["/login", "/signup"]; // 로그인 상태면 접근 불가

  const accessToken = request.cookies.get("accessToken")?.value;

  }

  if (isAuth &amp;&amp; accessToken) {
    // 이미 로그인된 상태라면 홈으로
  }
}</code></pre><p>여기서 Access Token뿐 아니라 Refresh Token의 존재 여부도 함께 확인하는 것이 포인트입니다. Access Token만 만료된 상태(둘 다 없는 게 아니라 Access Token만 없는 상태)라면 미들웨어 단계에서 바로 로그인 페이지로 보내지 않고, 실제 데이터 요청 시점에 <code>serverFetcher</code>가 재발급을 시도하도록 넘깁니다. 미들웨어는 "토큰이 아예 없는" 완전 미인증 케이스만 걸러내는 가벼운 1차 방어선인 셈입니다.</p><h2>서버 컴포넌트는 Route Handler를 거치지 않습니다</h2><p>Client Component가 로그인/로그아웃 같은 액션을 수행할 때는 <code>/api/auth/*</code> Route Handler를 호출하지만, Server Component가 데이터를 읽을 때는 한 단계를 생략합니다.</p><pre><code class="language-plaintext">Server Component ──(serverFetch)──&gt; Backend API Server (Route Handler 우회)</code></pre><p><code>next/headers</code>의 <code>cookies()</code>로 서버 컴포넌트 내부에서 직접 httpOnly 쿠키를 읽을 수 있기 때문에, 굳이 "브라우저 → Route Handler → 백엔드"로 이어지는 API Hop을 추가할 필요가 없습니다. 이 부분은 성능에 꽤 체감되는 차이를 만듭니다.</p><h2>로그인 상태를 클라이언트까지 물 흐르듯 넘기기</h2><p>SSR 프로젝트에서 흔히 겪는 문제는 "서버에서는 로그인 상태를 아는데, 클라이언트로 넘어가는 순간 깜빡임(flicker)이 생기는" 현상입니다. 이를 막기 위해 세 겹의 Provider를 둡니다.</p><ol><li><p><strong><code>AuthProvider</code></strong> (서버 컴포넌트) — 쿠키에 토큰이 있는지(<code>hasToken</code>)만 확인해서 다음 단계로 넘깁니다. 토큰 값 자체는 클라이언트로 내려주지 않습니다.</p></li><li><p><strong><code>AuthHydration</code></strong> — <code>/users/me</code>를 서버에서 미리 fetch해서 React Query 캐시에 채워 넣고 <code>dehydrate</code> 합니다. 401이면 <code>user: null</code>로 캐시를 세팅해 에러를 삼킵니다.</p></li><li><p><strong><code>AuthClientProvider</code></strong> — 클라이언트에서 <code>useUserQuery(hasToken)</code>로 이어받습니다. 서버에서 이미 채워둔 캐시가 있으니 추가 로딩 없이 바로 렌더링됩니다.</p></li></ol><pre><code class="language-typescript">const AuthContext = createContext&lt;AuthContextType&gt;({
  user: null,
  isLoading: false,
  isError: false,
  isAuthenticated: false,
});</code></pre><p>컴포넌트 트리 어디서든 <code>useAuth()</code>만 호출하면 로그인 상태를 알 수 있고, 실제 액션이 필요한 지점에서는 <code>useRequireAuth()</code>로 감싸서 "로그인 안 했으면 모달부터 띄우기" 같은 패턴을 재사용합니다.</p><pre><code class="language-typescript">const requireAuth = (callback?: () =&gt; void) =&gt; {
  if (!user) {
    loginModal.open();
    return false;
  }
  callback?.();
  return true;
};</code></pre><p>찜하기, 리뷰 작성처럼 로그인이 필요한 액션에 이 훅 하나만 붙이면 되므로, 페이지마다 로그인 체크 로직을 중복 작성하지 않아도 됩니다.</p><h2>소셜 로그인: 클라이언트는 "토큰 배달"만 합니다</h2><p>구글/카카오 로그인도 원칙은 같습니다. <strong>클라이언트는 OAuth 제공자로부터 받은 토큰(또는 인가 코드)을 BFF로 전달하는 역할만 하고, 실제 세션 관리는 서버가 전담합니다.</strong></p><p>카카오는 인가 코드 방식이라 한 단계가 더 있습니다.</p><pre><code class="language-plaintext">Browser → Kakao 로그인 → 인가 코드 수신
  → POST /api/auth/kakao (code 전달)
  → Next.js가 카카오 토큰 서버에 code 교환 요청
